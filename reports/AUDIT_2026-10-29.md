What this repo does: IT learning search and recommendations with a Python RAG API, a separate Express/PostgreSQL web application, and scheduled content collection. This audit assumes one API worker and sequential refresh jobs, as required by the existing deployment contract.

This is a scoped audit and remediation checkpoint, not a completed whole-repository audit or a production release approval. Ponytail ultra was applied before edits and to the resulting diff. No paid provider calls, database migrations, index activation, data deletion, or deployment were performed.

Must fix findings confirmed before edits:

1. **Rolling feeds remove valid archived content from the index** (`itlr/collect/runner.py`).
   - What this is: reconciliation marks documents absent from a source listing as missing; indexing excludes missing documents.
   - Problem: the configured DEV API uses per_page=30 and RSS/news listings contain recent articles, not complete inventories. An older article can disappear from a listing while its URL is still valid. A fixture reproduced missing=1 for that article.
   - Fix: absence is destructive only when the source explicitly declares `listing_is_complete: true`. The default is false; seen URLs can still restore missing records, including URLs beyond the fetch budget. Existing full-inventory reconciliation tests retain their deletion/restoration assertions with an explicit completeness flag.
   - If skipped: a refresh silently shrinks the real-data corpus. Fixed and regression tested. Previously missing documents absent from current feeds are not automatically recovered; review stored URLs separately before restoring them.

2. **String configuration can grant full-text permission** (`itlr/collect/sources.py`).
   - What this is: source policy controls whether article text may be retained.
   - Problem: `bool("false")` is true. Mistyped JSON silently grants permission.
   - Fix: require actual JSON booleans for both full-text and inventory-completeness policy. Six string/integer/null cases failed before and pass after the fix.
   - If skipped: content can be collected against the intended policy. Fixed; boolean defaults remain false. Invalid configurations now fail explicitly.

3. **Reported V2 nDCG uses the wrong rank discount** (`eval/eval_v2_real.py`).
   - What this is: the script reports retrieval ranking quality.
   - Problem: its private implementation divides gains by rank+1, not log2(rank+1). For ranks [2,1], grades {1:3,2:1}, it reports 0.739130 instead of 0.709810.
   - Fix: reuse `itlr.eval.metrics.ndcg_at_k`, with the complete relevance inventory as the ideal ranking. The numerical regression failed before and passes after.
   - If skipped: benchmark results labeled nDCG are not comparable to standard nDCG. Fixed. Historical V2 reports are not retroactively recalculated or presented as current measurements.

4. **Small real-data indexes fail the activation probe** (`itlr/indexv2.py`).
   - What this is: self-retrieval validates staging before activation.
   - Problem: two documents and top_k=5 cause numpy argpartition to raise ValueError.
   - Fix: cap top_k at catalog size and reject nonpositive limits or empty inputs explicitly. Reproduced failing case, then passing tests.
   - If skipped: a small curated corpus cannot pass this probe. Fixed.

Should fix / remaining work:

5. **V2 does not retain a searchable chunk-vector index** (`itlr/pipelines/build_embeddings_v2.py`).
   - What this is: chunks are encoded separately, then averaged into one item vector; chunk metadata is retained without chunk vectors.
   - Problem: a specific passage can be diluted by unrelated passages. This is an architectural gap against the requested V3, not a measured retrieval regression.
   - Fix: persist chunk vectors and ownership, integrate retrieval and evidence selection, preserve item response contracts, and compare on independently labeled passage queries before activation.
   - If skipped: the system remains item retrieval with chunk-derived embeddings. Not implemented in this checkpoint; do not label it completed V3.

6. **Refresh needs an explicit concurrency contract** (`itlr/versioning.py`).
   - What this is: version IDs have second precision and history updates use read/modify/write.
   - Problem: concurrent refresh invocations in the same second can share a staging directory. No locking is visible in these functions.
   - Fix: serialize refresh/build at the orchestration boundary and test two concurrent invocations before allowing overlapping jobs.
   - If skipped: overlapping jobs risk mixed staging artifacts and lost history. Unresolved; run only one refresh job at a time. Not approved for overlapping refresh production use.

Verdict: fixes 1–4 are suitable for review; full production release remains blocked by unfinished V3 and release verification. No unhandled Critical defect was established by this scoped review; absence of findings is not a security certification.
